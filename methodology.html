Research Protocol / v0.1

Evidence before certainty.

The methodology behind the Foundation Model Atlas: how model and architecture records are defined, sourced, normalized, connected, compared and updated — while keeping documented facts separate from interpretation.

01 / Scope

What the Atlas is trying to represent.

The Atlas is a structured research index of foundation models and the architectural systems used to build them. Its purpose is not merely to collect names, but to make model identity, architecture, lineage and evidence navigable.

Core rule: a field should communicate what the available evidence supports — not what would merely be plausible from a model's name, family or reputation.
Model record

Identity + capabilities

Name, organization, release information, parameter conventions, modalities, context, licensing, links and other documented attributes.

Architecture record

Mechanism + topology

Architecture family, attention or sequence mechanism, routing, positional strategy, mixing, modality interfaces and other structural properties when documented.

02 / Record Model

One source of truth per entity.

Models and architectures should be stored as structured records rather than repeated manually across pages. Web pages are presentation layers; JSON records are the underlying data layer.

01

Stable identity

Each record receives a stable identifier suitable for URLs, joins and comparison.

02

Normalized fields

Comparable concepts use consistent field names and units wherever possible.

03

Explicit unknowns

Unavailable information should remain unavailable instead of being silently fabricated or inferred.

04

Provenance attached to claims

Important technical claims should be traceable to a source record or primary evidence.

03 / Evidence

Source hierarchy.

The strongest evidence generally comes from material produced by the model's creators or from the original technical publication. Secondary sources are useful for discovery and cross-checking, but should not silently replace primary evidence.

PriorityEvidenceUse
01Original technical paper / technical reportArchitecture, training method, experiments and technical claims.
02Official model card / release documentationIdentity, variants, parameters, context, modalities, license and usage information.
03Official repository / implementationConfiguration, module structure, code-level architectural details.
04Official weights / configuration artifactsMachine-readable configuration and implementation evidence where publicly available.
05Official benchmark / evaluation materialReported performance and evaluation methodology.
06Reputable secondary researchDiscovery, triangulation and context when primary evidence is incomplete.
Evidence is claim-specific. A source proving a parameter count does not automatically prove an attention mechanism, and a paper describing a family does not automatically prove that every later variant has the same architecture.

04 / Certainty

Fact, normalization, inference.

The Atlas should make the epistemic status of information legible.

Documented

Direct evidence

The source explicitly states or exposes the property. This is the strongest form of record-level evidence.

verifiedprimary source
Normalized

Equivalent representation

The Atlas reformats a documented value into a consistent representation without changing its substantive meaning.

normalizedcomparable
Inferred

Reasoned interpretation

A conclusion is derived from evidence rather than stated directly. It should be clearly labeled and never presented as a direct quote from the source.

inferredreview needed
Unavailable

No supported value

The public evidence does not support a reliable value. Leaving a field unknown is preferable to filling it with an assumption.

unknownnot disclosed

05 / Architecture

Represent structure without pretending to know more.

Architecture records describe computational mechanisms at the level supported by the evidence. A visual diagram can be explanatory, but it should not imply undocumented exact layer counts, routing topology or tensor shapes.

Sequence

Core mechanism

Capture the principal sequence-processing mechanism such as attention, state-space processing, recurrence or a hybrid combination when supported.

Attention

Attention strategy

Represent mechanisms such as MHA, MQA, GQA, local/sliding attention or other documented variants where applicable.

Sparse compute

Expert routing

For MoE systems, distinguish total experts, active experts and routing behavior when those details are available.

Multimodal

Modality interface

Describe encoders, projectors, adapters, cross-attention or shared representations only to the degree supported by source material.

Architecture abstraction rule: a conceptual family label such as “Transformer” is not a substitute for the model's documented architecture. The detailed record should preserve meaningful differences.

06 / Parameters

Parameter counts need context.

Parameter counts can be misleading when models use sparse expert architectures or publish several variants. The Atlas should preserve the distinction between total and active parameters where the source provides it.

NotationMeaningExample interpretation
TotalAll stored parameters in the model.Useful for model scale and storage comparisons.
ActiveParameters participating in a typical token's computation.Important for sparse/MoE compute comparisons.
A/BCommon shorthand for active/total or a source-specific convention.Must be interpreted using the originating source rather than assumed universally.
VariantA separately released model size or configuration.Do not merge distinct variants into one record merely because their names share a family.

07 / Families & Lineage

Family is not identity.

Model families connect related releases while preserving individual model records. A family relationship should not cause attributes from one generation to be copied blindly into another.

FAMILY

Shared lineage

Models can belong to the same research or product family while differing in scale, architecture, training data, modality or deployment configuration.

VERSION

Generation / release

Versions should remain distinguishable when their technical or release identity is materially different.

VARIANT

Size / specialization

Small, large, coder, reasoning, multimodal and other variants may share lineage without being interchangeable records.

08 / Provenance

Sources are first-class records.

A source should be represented as data that can be reused by model pages, architecture pages, comparison views and future audits.

{
  "id": "source-001",
  "type": "technical_report",
  "title": "Original technical report",
  "publisher": "Organization",
  "url": "https://...",
  "accessed": "YYYY-MM-DD",
  "supports": [
    "architecture",
    "parameters"
  ]
}

The exact schema can evolve, but the principle is stable: **do not bury provenance only inside page prose**.

09 / Comparison

Compare evidence-backed structures.

The Comparison Lab should compare normalized fields and documented components rather than visual similarity alone.

A

Normalize first

Make units, naming and categorical representations comparable before calculating differences.

B

Show differences explicitly

Highlight changed components such as attention strategy, routing, sequence mechanism, parameter regime or modality interface.

C

Preserve unknowns

An unknown field should not be treated as a difference simply because the other model has a documented value.

D

Explain the visual

Interactive diagrams are explanatory interfaces to structured records, not independent evidence.

10 / Maintenance

Updates, deduplication and version control.

The Atlas should prefer deterministic updates over repeated manual edits across HTML pages.

Deduplication

One entity, one canonical ID

Before adding a record, check normalized name, organization, release/version and existing IDs. Near-duplicates should be reviewed rather than silently accumulated.

Updates

Change the data, regenerate views

When a model or architecture changes, update the canonical JSON/source record first. Presentation pages should read the updated data.

Audit

Keep provenance inspectable

Important changes should be traceable to a source or explicit editorial decision.

Freshness

Release-aware maintenance

New model releases should not overwrite historical identity. Add or update records according to whether the event is a new model, version, variant or correction.

11 / Limitations

What the Atlas cannot guarantee.

Public model information is uneven. Some organizations disclose detailed architecture papers; others disclose only high-level descriptions. Closed models can have particularly limited technical transparency.

Therefore: completeness of the database does not mean completeness of public knowledge. A missing field can be a property of the evidence landscape, not a failure of the Atlas.

Architecture diagrams may also simplify complex implementations. Hardware kernels, serving optimizations, quantization, inference-time routing and proprietary training infrastructure can sit outside the model's conceptual architecture record.

12 / Principles

The Atlas contract.

01

Primary evidence first.

Prefer original technical and official sources for technical claims.

02

Facts before inference.

Separate documented properties from interpretations and mark uncertainty.

03

Entities before pages.

Canonical records are the source of truth; HTML interfaces expose them.

04

Comparability without false precision.

Normalize what can be normalized, but preserve meaningful differences and unknowns.

05

Visuals explain; evidence supports.

An animated architecture diagram is an interface for understanding, not proof of an undocumented implementation detail.

06

History remains history.

New releases should extend the Atlas rather than erase the lineage that came before them.
